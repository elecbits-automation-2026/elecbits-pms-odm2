eb-core-database-1 — one database, six tools

A thin shared spine in core, one private schema per tool, and a migration path whose first four stages touch none of the repositories you have already built.

Tools pms-odm · boxbuild · sales · finance · hr · mgmt Backend Supabase Postgres · Google Drive · Vercel Drafted 9 Aug 2026

The one decision everything else follows from

Which schema owns the words project, client and person.

Today public.projects and public.clients already exist, and they are ODM-shaped — they carry lld_customer, lld_designer, sanctioned. A box-build run has none of those and needs a line rate and a yield figure instead. If the shared project table lives in public, every new tool either bends its work to fit ODM columns or bolts nullable columns onto a table three other tools read. Within a year that table has sixty columns and nobody dares drop one.

So the spine does not live in public. It lives in a new schema called core, it is deliberately small, and public is frozen the day core is created.

Shared identity, private detail. core.projects holds only what is true of every project in the company — a code, a kind, a client, a state, an owner, some dates. Everything a particular tool needs goes in that tool's own project_detail table, keyed on the same primary key. One project, one id, six different opinions about it.

Why one table for clients and vendors

Half your vendors will eventually buy something from you, and two of your clients already supply components. Model them as separate tables and you will maintain the same company's GSTIN in two places and reconcile them by hand forever. core.orgs is a company we deal with; core.org_roles says in what capacity, and a company can carry several rows there at once. Finance joins invoices to orgs playing client and bills to orgs playing vendor — same table, different role.

The same argument applies to core.people: one row per human, whether they are staff, a contractor, or a client-side engineer who shows up in a MoM. What they are paid and what their title is are HR facts, and they live in hr.employment and hr.salary, behind a separate lock.

Keep this schema small on purpose. The test for a new column here is not “is it useful?” — it is “would all six tools mean the same thing by it?” If not, it belongs in a tool schema.

Payslips, offer letters, contracts

These are files, so they belong in core.documents like everything else — but a payslip must not be readable by anyone who can read a gerber. Give those rows a kind of payslip / offer / contract_employment and add one extra policy on core.documents: rows with those kinds are visible only to HR admins and to the person they concern. It is the single exception to core being freely readable, and it is worth writing down as one.

mgmt one table and a handful of views — the payoff for all of the above
  • mgmt.okrsThe only real table: objective, key result, target, current, scoped to company, team or person.
  • mgmt.v_project_healthOne row per project: state, days to due, open and overdue tasks, hours booked, invoiced against sanctioned, cash received. Reads core, pms, hr and finance — and is possible only because they all agree on project_id.
  • mgmt.v_org_360Per client: open deals, running projects, lifetime invoiced, outstanding, last contact. The question Sales and Finance each answer half of today.
  • mgmt.v_person_loadPer person: projects, open tasks, hours this week, leave booked ahead. Staffing decisions without a spreadsheet.
  • mgmt.v_company_pulseA single row: cash in and out this month, pipeline value, work in progress, headcount, overdue receivables.

One function guards the whole database

Six tools × forty tables is a lot of RLS policies, and hand-written policies drift. So the permission question is asked in exactly one place — core.can(tool, level) — and every policy in every schema is a one-liner that calls it. Change someone's access by updating one row in core.grants; no policy is ever edited to onboard a person.

create schema core;
create table core.grants (
  person_id uuid references core.people(id) on delete cascade,
  tool      text not null,
  level     text not null check (level in ('none','read','write','admin')),
  primary key (person_id, tool));

-- the caller's row in the roster, or null if they are not on it
create function core.me() returns uuid
language sql stable security definer set search_path = core as $$
  select id from core.people where auth_id = auth.uid();
$$;

-- does the caller hold at least `_level` on `_tool`?
create function core.can(_tool text, _level text) returns boolean
language sql stable security definer set search_path = core as $$
  select exists (
    select 1 from core.grants g
    where g.person_id = core.me() and g.tool = _tool
      and array_position(array['none','read','write','admin'], g.level)
       >= array_position(array['none','read','write','admin'], _level));
$$;

-- and then, forty times over, one line each
alter table hr.salary enable row level security;
create policy read_salary on hr.salary for select to authenticated
  using (core.can('hr','admin') or person_id = core.me());
create policy write_salary on hr.salary for all to authenticated
  using (core.can('hr','admin')) with check (core.can('hr','admin'));

How none of this disturbs the repos you have built

The PMS reads public.profiles. Once core.people is the real table, that name becomes a view over it — and because the view is declared security_invoker = on, it runs with the caller's own permissions, so core's policies still apply. The app sends the same query and gets the same columns back. Nothing is redeployed; the cut-over is two SQL statements and the rollback is two more.

Rollout

Stages 0–3 touch no existing repository. That is not a coincidence in the ordering — it is the point of it. You can stop after stage 3 and stay there indefinitely with HR and Finance fully live.

  1. 00

    Create the schemas, empty

    create schema core, pms, boxbuild, sales, finance, hr, mgmt; then every table above, with RLS enabled from the first statement. Add core to Supabase → Settings → API → Exposed schemas. Not one row of data, not one app aware of it.

    no repo touched
  2. 01

    Identity and the lock

    Seed core.people from public.profiles, carrying auth_id across so existing logins keep working. Seed core.grants for the current team. Write core.me() and core.can(), then the policies. Verify by signing in as two different people and selecting from hr.salary — one should see one row, the other zero.

    no repo touched
  3. 02

    Backfill the spine

    public.clients → core.orgs + a client role row. public.projects → core.projects + pms.project_detail. The PMS's live data currently sits in app_kv as two JSON blobs, so this is a parse-and-insert, not a table copy — write it as an idempotent script you can re-run while both stores are live.

    no repo touched
  4. 03

    Build HR and Finance on core only

    Greenfield, so they never see public and inherit none of its shape. Each is its own Vercel project and its own repo, pointing at the same Supabase URL with createClient(url, key, { db: { schema: 'hr' } }). From day one they read real clients and real projects, because the spine is already populated.

    new repos only
  5. 04

    Point the PMS at core, without deploying it

    Rename public.profiles to profiles_legacy, create the security_invoker view in its place, confirm the app still works, drop the legacy table a week later. Repeat per table. Every step is reversible in one statement.

    no repo touched
  6. 05

    Move Sales off the blob — and off the anon key

    The only stage that requires a code change in a repo you have already shipped, and it should be done together with switching Sales from its own sales:users login to Supabase Auth. Until that lands, see the note below.

    sales repo

The one thing that must not be skipped

The Sales tool authenticates in its own application code against rows in sales:users, which means it hands the Supabase anon key to every visitor of its URL. Today that is contained: collections is the only object anon can reach, and the migration you already have removes the blanket anon grant that the PMS schema left behind.

The moment salary rows and invoices live in the same database, “anon can reach exactly one table” stops being hygiene and becomes load-bearing security. So: do not add hr or finance to Supabase's Exposed schemas while Sales still ships the anon key to the browser. Until stage 5 lands, those two tools should reach Postgres only from server-side code holding the service role — a Vercel route or an edge function — never from the browser.

Seven conventions, decided once

  1. A tool schema may reference core, never another tool schema. Cross-tool questions are answered by a mgmt view. Break this once and the six tools become one tool with six front-ends.
  2. Money is numeric(14,2) beside a currency char(3). No floats, no implied INR, no totals stored where they can be summed.
  3. Instants are timestamptz, dates are date. Never bare timestamp — it is the column type that silently loses an invoice a day.
  4. Enumerations are text with a check, not Postgres enum types. Adding a status to a check constraint is one statement; adding a value to an enum inside a transaction is a footgun you will meet at a bad moment.
  5. Every table gets id uuid default gen_random_uuid(), created_at, and RLS enabled in the same migration that creates it. A table that ships without a policy ships open.
  6. Nothing in core is hard-deleted. core.events references it. Set archived_at and filter in the view.
  7. One numbering authority. Every Eb- code comes from core.numbering, so Sales quoting a job and PMS opening it cannot mint the same code twice.

What I would do this week

Stage 0 and stage 1 are a single afternoon and carry no risk to anything running — the schemas are empty and nothing reads them. They are also the part that gets harder the longer HR and Finance wait, because every table those tools add outside core is a table that later has to be moved. Everything after that can wait for a quiet week.
